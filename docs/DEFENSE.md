# МемоМастер: материалы для защиты

## 1. Подготовка к демонстрации (за 10 минут до защиты)

1. PostgreSQL запущен (`docker compose ps` или служба), `python -m alembic upgrade head` выполнен.
2. В `.env` есть `BOT_TOKEN`, `DATABASE_URL`, желательно `GIPHY_API_KEY`.
3. `python -m app.main` → в логе «Бот запущен, ожидаю сообщения». Терминал оставьте на экране: на нём видно логи.
4. Для показа лидерборда и ленты заранее подготовьте 2–3 тестовых аккаунта (друзья или второй Telegram): сыграйте с них по одной игре и опубликуйте по мему.
5. Запасной план: если интернет подведёт, покажите `python -m pytest` (391 тест без интернета) и логи.

## 3. Ключевые решения и аргументы

| Решение | Почему так (аргумент для защиты) |
|---|---|
| aiogram 3 + long polling | не нужны публичный адрес и HTTPS; обработчики описываются декораторами; встроенные FSM и middleware |
| PostgreSQL + SQLAlchemy async | надёжные транзакции и ограничения целостности; async не блокирует бота на запросах |
| Alembic | схема версионируется; БД создаётся командой, а не вручную |
| Кэш в памяти вместо Redis | один процесс бота; Redis только усложнил бы запуск. Интерфейс совместим, замена затронет один класс |
| Сервисы отдельно от хендлеров | бизнес-логику можно тестировать без Telegram; хендлеры остаются тонкими |
| Один `ApiClient` | timeout, retry и разбор ошибок в одном месте, а не копии в трёх сервисах |
| `MemoryStorage` для FSM | проще; цена: игры сбрасываются при перезапуске (бот это учитывает и сообщает «игра устарела») |
| Без `relationship()` | в async «ленивая» подгрузка не работает, явные JOIN понятнее |
| Ограничения в БД, а не только в коде | защищают от гонок (двойные нажатия), которые код проверить не успевает |
| Вопросы в JSON и загрузка в БД при старте | контент правится без кода; загрузка идемпотентна по `slug` |

## 4. Объяснения «простым языком»

**async/await.** Бот ждёт сеть и БД. `await` означает «подожди результат, а пока обслужи других». Без него один медленный запрос блокировал бы всех.

**ORM.** Таблица это Python-класс, строка это объект. Запросы собираются из Python-выражений, поэтому нет ручного SQL и SQL-инъекций.

**FSM.** Бот помнит, на каком шаге сценария находится пользователь, и принимает только уместные действия.

**Dependency injection.** Сервисы создаются один раз в `main.py` и передаются в `Dispatcher`. Хендлеру достаточно объявить параметр `giphy: GiphyService`, и aiogram подставит объект. Для тестов подставляются подделки.

**Кэш с TTL.** Запомнить ответ API на время и не ходить в сеть, пока он «свежий».

**Retry с backoff.** Временный сбой (таймаут, 5xx, 429) повторяется до 3 раз с растущей паузой и случайной добавкой. Ошибки без смысла повторять (неверный ключ, 404) не повторяются.

**Graceful degradation.** Падение внешнего сервиса отключает только его функцию, а не весь бот.

**Миграции.** Версионированные скрипты изменения схемы БД. Применяются командой `python -m alembic upgrade head`.

**Атомарное обновление.** `UPDATE ... SET likes = likes + 1` выполняется в БД целиком. Вариант «прочитал, прибавил в Python, записал» теряет голоса при параллельных нажатиях.

## 5. Вопросы преподавателя и ответы

**Архитектура**

1. *Почему слои handlers / services / database?* Чтобы каждая часть отвечала за своё: хендлер за диалог, сервис за правила, БД за хранение. Логику можно тестировать без Telegram, API можно заменить, не трогая хендлеры.
2. *Зачем middleware?* Чтобы на каждый апдейт автоматически открыть сессию БД (commit/rollback) и найти или зарегистрировать пользователя. Иначе этот код дублировался бы в каждом хендлере.
3. *Почему не webhook?* Нужен публичный HTTPS-адрес. Для учебного запуска long polling проще; в продакшене лучше webhook.
4. *Что будет, если запустить два экземпляра бота?* Конфликт: Telegram отдаёт апдейты одному процессу (`TelegramConflictError`).
5. *Как масштабировать?* Перейти на webhook, заменить `MemoryStorage` и кэш на Redis, запустить несколько экземпляров за балансировщиком. БД уже поддерживает параллельность.

**FSM**

6. *Зачем FSM, если можно хранить шаг в БД?* FSM в aiogram как раз хранит состояние и данные пользователя; привязка хендлеров к состояниям убирает ручные проверки «на каком я шаге».
7. *Что при перезапуске бота?* Состояния в памяти теряются. Старые кнопки обрабатываются последним хендлером и отвечают «игра устарела»; пользователь начинает заново.
8. *Как защищены от двойного нажатия на ответ?* Два уровня: состояние меняется на `reviewing` до записи (повторное нажатие уже не подходит фильтру), плюс `UNIQUE(session_id, question_id)` в БД на случай одновременных апдейтов.

**БД**

9. *Какие связи между таблицами?* Пользователь → игры → ответы (один ко многим); вопрос → ответы; пользователь → мемы → голоса; пользователи ↔ достижения (многие ко многим через `user_achievements`).
10. *Как предотвращено повторное голосование?* `UNIQUE(user_id, meme_id)`: вторая вставка падает с `IntegrityError`, которую сервис превращает в «уже голосовал». Это работает даже при гонке.
11. *Зачем счётчики лайков в таблице мемов, это же дубль?* Денормализация ради скорости ленты: не считать голоса при каждом показе. Консистентность держится тем, что голос и счётчик меняются в одной транзакции.
12. *Зачем индекс по `users.xp`?* Лидерборд сортирует и считает место по XP. Проверено: топ и место на 20 000 игроков за ~14 мс.
13. *Почему картинки мемов не в БД и не на диске?* Telegram хранит файл и выдаёт `file_id` для повторной отправки. Это проще и не занимает место.
14. *Что такое миграция и зачем?* Версионированное изменение схемы. Любой может получить нужную схему одной командой, а изменения схемы остаются в истории Git.
15. *Почему категории строкой, а не ENUM PostgreSQL?* Строки проще мигрировать (ENUM трудно менять), а допустимые значения проверяет Python (`QuizCategory`).

**API, кэш, ошибки**

16. *Как работает retry?* Повторяются только временные ошибки (таймаут, обрыв, 5xx, 429). Пауза растёт вдвое с небольшой случайной добавкой. При 429 уважается `Retry-After`, но не дольше 5 с, потому что пользователь ждёт.
17. *Что если Giphy / Imgflip / Reddit недоступны?* Бот продолжает работать: без GIF-реакции, на запасных шаблонах (цветной фон), с запасным «мемом дня». Пользователь получает объяснение.
18. *Как работает кэш?* Смотрим в кэше по ключу; если запись свежая — отдаём; иначе идём в API и кладём результат на TTL. Размер ограничен (500 записей).
19. *Почему не Redis?* Один процесс, учебный проект; усложнение не оправдано. Совместимый интерфейс позволяет заменить.
20. *Как обеспечена безопасность?* Секреты в `.env` (в `.gitignore`), токен как `SecretStr`, маскировка секретов в логах, ORM без ручного SQL, проверка и ограничение ввода, экранирование HTML, проверка размера и формата фото, whitelist хостов картинок, фильтр контента Reddit.
21. *Что мешает подделать callback_data?* Данные кнопок разбираются типизированными классами; значения проверяются (категория из списка, номер варианта в пределах, номер вопроса совпадает с текущим). Подделка даёт понятный ответ («устарело» или «неизвестная категория»), а не ошибку.
22. *Почему Reddit необязателен?* Reddit с ноября 2025 требует одобрения API. Раздел реализован полностью, но без ключей включается запасной режим; это же демонстрация graceful degradation.

**Геймификация**

23. *Как считается уровень?* `floor(sqrt(xp/50)) + 1`; XP для уровня L: `50·(L−1)²`. Растущая стоимость уровней замедляет прокачку.
24. *Как добавить новое достижение?* Одна запись в каталог `ACHIEVEMENTS` (метрика + цель); выдача идемпотентна благодаря составному первичному ключу.
25. *Как считается место в лидерборде вне топа?* `COUNT` игроков, которые стоят выше по правилу сортировки (больше XP, а при равенстве меньший id), плюс один; таблица целиком не загружается. Игроки с нулём XP в рейтинг не попадают.

**Тесты**

26. *Что тестируете и как без Telegram?* Сервисы тестируются напрямую на SQLite в памяти. Хендлеры тестируются через настоящий `Dispatcher` и поддельную сессию Telegram: подаём «сырые» апдейты и проверяем ответы и записи в БД. API подменяется поддельным клиентом.
27. *Как проверяли гонки?* Отдельными скриптами на настоящем PostgreSQL: параллельные ответы, голоса, выдача достижений. Уникальные ограничения срабатывают, дублей нет.
28. *Откуда уверенность, что тест что-то проверяет?* Для ключевых проверок ломался код и тест падал (мутационная проверка): например, убрали маскировку `api_key` или проверку «пользователь-бот», и тесты упали.

**Контент**

29. *Откуда вопросы? Не выдуманы ли факты?* Вопросы про мемы 2025–2026; факты проверены по открытым источникам (Brand Analytics, Know Your Meme, СМИ). Спорные детали в вопросы не включались. Любой вопрос можно заменить в `questions.json`.
30. *Что с авторскими правами?* Картинки в репозиторий не кладутся: используем API и URL (Giphy, Imgflip, Reddit). Шрифт системный.

## 6. Ограничения проекта (честно)

- Состояния FSM и кэш живут в памяти процесса: при перезапуске сбрасываются, несколько экземпляров бота работать не будут.
- Нужны живые проверки в Telegram: автотесты не видят реальный Telegram, Giphy и внешний вид сообщений.
- Вопросы по мемам стареют быстро: список стоит обновлять.
- Reddit требует одобрения доступа; без него «Мем дня» работает в запасном режиме.
- Уведомления ограничены одним случаем: автор получает сообщение, когда рейтинг его мема принёс бонус (если уведомления включены). Общих рассылок нет.
