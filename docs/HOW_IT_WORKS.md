## 1. Бот за одну минуту

Бот это одна программа на Python (`python -m app.main`), которая постоянно спрашивает у Telegram «есть новые сообщения?» (long polling). Каждое сообщение или нажатие кнопки приходит как **апдейт**. Бот обрабатывает апдейт и отвечает.

Внутри программа разделена на слои. Каждый слой делает своё и обращается только к слою ниже:

```
Telegram ─► middleware ─► handler ─► service ─► БД (PostgreSQL)
                                         └────► кэш ─► внешний API (Giphy, Imgflip, Reddit)
```

| Слой | Пример | За что отвечает |
|---|---|---|
| handler | `app/bot/handlers/quiz.py` | диалог: принять кнопку, показать экран |
| service | `app/services/quiz_service.py` | правила: правильный ли ответ, сколько XP |
| models | `app/database/models/quiz.py` | как данные лежат в таблицах |
| core | `app/core/http.py`, `cache.py` | общие инструменты: HTTP с повторами, кэш |

Главная мысль для защиты: **сервисы не знают про Telegram**, а **хендлеры не знают про SQL и HTTP**. Поэтому сервисы проверяются обычными тестами, а внешний API можно заменить, не трогая диалог.

## 2. Путь одного нажатия кнопки

Пример: Аня играет в MNBA, видит третий вопрос и нажимает вариант **B**.

**Шаг 1. Telegram присылает апдейт.** В нём, среди прочего, `callback_query.data = "quiz:ans:1:2"`: действие «ответ», вариант №1 (B, счёт с нуля), вопрос №2 (третий, счёт с нуля).

**Шаг 2. Middleware.** До хендлера апдейт проходит две «обёртки»:

- `DbSessionMiddleware` (`app/bot/middlewares/db.py:24`) открывает сессию БД;
- `UserMiddleware` (`app/bot/middlewares/user.py`) находит Аню в таблице `users` по `telegram_id` (или регистрирует, если её нет) и кладёт объект пользователя в параметр `user`.

**Шаг 3. Выбор хендлера.** aiogram ищет хендлер, у которого совпали фильтры:

```python
@router.callback_query(QuizStates.answering, QuizCB.filter(F.action == "ans"))   # quiz.py:119
async def handle_answer(callback, callback_data, state, user, session): ...
```

Два условия: Аня сейчас в состоянии `answering` **и** кнопка это ответ. Если бы она нажала старую кнопку из прошлой игры, состояние не совпало бы, и сработал бы последний хендлер `stale_quiz_button` (`quiz.py:219`) с сообщением «Эта игра уже неактуальна».

**Шаг 4. Проверки в хендлере.** Номер вопроса из кнопки (`q=2`) сравнивается с текущим из FSM; номер варианта должен быть в пределах 0–3. Затем состояние сразу меняется на `reviewing`: повторное нажатие той же кнопки уже не пройдёт фильтр.

**Шаг 5. Сервис.** `QuizService.submit_answer` (`app/services/quiz_service.py:131`):

1. сравнивает выбранный текст с правильным ответом;
2. считает серию и XP;
3. вставляет строку в `quiz_attempts` (если такая уже есть, БД отклонит вставку, см. раздел 9);
4. обновляет счётчики игры и XP пользователя.

**Шаг 6. Экран.** Хендлер вызывает `show_screen`, и сообщение с вопросом **редактируется** в экран с ответом (новое сообщение не создаётся). Затем бот «отвечает» на нажатие, чтобы у кнопки пропали часики.

**Шаг 7. Commit.** Хендлер закончился без ошибок, middleware делает `commit`: ответ, XP и серия сохраняются одновременно. Если бы случилась ошибка, был бы `rollback`, и в БД не осталось бы «половины» ответа.

## 3. callback_data: что лежит в кнопке

У inline-кнопки есть скрытая строка до 64 байт. Её собирают и разбирают классы из `app/bot/callbacks.py`, поэтому строки вручную не парсятся.

| Объект в коде | Строка в кнопке |
|---|---|
| `MenuCB(action="play")` | `menu:play` |
| `QuizCB(action="cat", value="nba")` | `quiz:cat:nba:0` |
| `QuizCB(action="ans", value="2", q=3)` | `quiz:ans:2:3` |
| `QuizCB(action="next", q=3)` | `quiz:next::3` |
| `MemeCB(action="tpl", value="181913649")` | `meme:tpl:181913649:0` |
| `CommunityCB(action="vote", sort="pop", page=0, meme_id=17, value=1)` | `comm:vote:pop:0:17:1` |

Обратно: `QuizCB.unpack("quiz:ans:2:3")` → `action='ans' value='2' q=3`.

**Почему это безопасно.** Строку можно подделать (её присылает клиент). Поэтому каждое значение проверяется: категория должна быть из списка, номер варианта в пределах, номер вопроса совпадать с текущим, мем существовать и быть опубликованным. Тест `tests/test_edge_cases.py` подаёт 7 видов «мусорных» строк, и бот ни разу не падает.

## 4. FSM на примере игры

FSM (конечный автомат) хранит, **на каком шаге** находится пользователь, и **данные текущей игры**. Состояния объявлены в `app/bot/states/quiz.py`.

Пример игры Ани:

| Действие | Состояние до | Состояние после | Что в `state.data` |
|---|---|---|---|
| нажала «🎮 Играть» | — | `choosing_category` | пусто |
| выбрала MNBA | `choosing_category` | `answering` | `session_id=21, question_ids=[7,3,12,5,9], index=0, options=[...], level_before=1` |
| нажала вариант | `answering` | `reviewing` | без изменений |
| нажала «Дальше» | `reviewing` | `answering` | `index=1`, новые `options` |
| … ещё 4 вопроса … | | | |
| «Дальше» после 5-го | `reviewing` | `finished` | — |
| «Играть ещё» | `finished` | `choosing_category` | данные очищены |

Что даёт FSM на практике:

- **Нельзя ответить дважды:** после ответа состояние `reviewing`, а хендлер ответа принимает только `answering`.
- **Двойной тап обрабатывается по очереди:** апдейты одного пользователя выполняются строго друг за другом (`SimpleEventIsolation`, `app/bot/dispatcher.py`). Пример: Аня дважды быстро нажала «Дальше». Первое нажатие показывает следующий вопрос и сохраняется, второе ждёт и видит уже новый номер вопроса, поэтому получает «устарело», а не второй экземпляр вопроса. Апдейты разных пользователей при этом идут параллельно.
- **Нельзя ответить на чужой вопрос:** номер вопроса в кнопке должен совпасть с `index`.
- **Генератор мемов** использует свой автомат (`app/bot/states/meme.py`): бот различает «это верхний текст» и «это нижний текст», хотя оба приходят обычными сообщениями.

Состояния хранятся в памяти (`MemoryStorage`). Если бот перезапустить посреди игры, состояние потеряется, и старые кнопки ответят «игра неактуальна». Это осознанное упрощение.

## 5. Викторина изнутри

**Подбор вопросов** (`quiz_service.py:90`). Сначала берутся случайные активные вопросы категории, на которые пользователь **ещё не отвечал**. Если таких меньше пяти, добираются уже виденные. Для «Смешанной» фильтра по категории нет.

**Варианты** (`quiz_service.py:123`). Правильный ответ и три неправильных перемешиваются, поэтому правильный не всегда под буквой A.

**Проверка.** Сравнивается текст выбранного варианта с `correct_answer`. Бот берёт текст по номеру из FSM (`options[choice]`), а не из кнопки, поэтому подменить ответ через `callback_data` нельзя.

**Откуда вопросы.**

- 43 вопроса в `app/content/questions.json`. При запуске они загружаются в таблицу `quiz_questions` по `slug`: повторный запуск обновляет вопросы, а не создаёт дубли.
- 8 визуальных вопросов «Что это за мем?» из `app/content/gif_questions.json`. Для них бот ищет картинку или GIF в Giphy и отбрасывает варианты, где ответ написан прямо на картинке.

**Как выглядит вопрос** (реальный вывод `format_question`):

```

C. Сигнал партнёрам для заслона

```

**Правильный ответ:**


**Неправильный ответ:**


**Итог игры:**


## 6. XP и уровни: считаем руками

Все правила в одном файле `app/services/xp.py`.

**Формула XP за правильный ответ** (`xp.py:47`): `10` + надбавка за сложность (`0 / 2 / 5`) + `5`, если это третий или следующий правильный ответ подряд.

**Пример 1. Идеальная игра** (сложности вопросов 1, 2, 3, 2, 1):

| Вопрос | Сложность | Серия | XP |
|---|---|---|---|
| 1 | 1 | 1 | 10 |
| 2 | 2 | 2 | 10 + 2 = 12 |
| 3 | 3 | 3 | 10 + 5 + 5 = 20 |
| 4 | 2 | 4 | 10 + 2 + 5 = 17 |
| 5 | 1 | 5 | 10 + 5 = 15 |
| бонус 5/5 | | | 20 |
| **итого** | | | **94** |

**Пример 2. Одна ошибка** (все сложности 1; верно, верно, ошибка, верно, верно): 10 + 10 + 0 + 10 + 10 = **40 XP**. Ошибка обнуляет серию, поэтому бонуса за серию нет, и бонуса 5/5 тоже нет.

**Уровень** (`xp.py:27`): `level = floor(sqrt(xp / 50)) + 1`.

| Уровень | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| нужно XP суммарно | 0 | 50 | 200 | 450 | 800 | 1250 | 1800 |

После примера 1 у новичка 94 XP: это уровень 2, прогресс `44/150` (на уровне 2 он набрал 94 − 50 = 44, а весь уровень 2 занимает 200 − 50 = 150 XP). В профиле это видно как полоска `▰▰▰▱▱▱▱▱▱▱ 44/150`.

**Другие источники XP:** мем создан +5, опубликован +5, рейтинг мема впервые достиг +5: автору +10 (один раз).

## 7. Достижения

Каждое достижение это **метрика + цель** (`app/services/achievements.py:63`). Например, `Hooper`: метрика «правильных ответов в MNBA и WNBA», цель 10.

Пример. Аня сыграла первую игру на 5 из 5 в MNBA. После игры `check_and_award` (`achievements.py:164`) собирает статистику (побед: 1, идеальных игр: 1, правильных в баскетболе: 5 …) и сравнивает с целями:

| Достижение | Метрика | Цель | Результат |
|---|---|---|---|
| 🏆 First Win | 1 победа | 1 | выдано |
| 🎯 Без права на ошибку | 1 идеальная игра | 1 | выдано |
| 🏀 Hooper | 5 ответов | 10 | прогресс 5/10 |
| 🧠 Big Brain | серия 5 | 20 | прогресс 5/20 |

Почему одно достижение нельзя получить дважды: у `user_achievements` первичный ключ из двух полей `(user_id, achievement_id)`. Вторая такая строка просто не вставится.

## 8. Генератор мемов

Путь от кнопки до картинки:

1. `/meme` → состояние `choosing_template`. Бот показывает шаблоны Imgflip по 8 на странице (список кэшируется на 6 часов).
2. Выбор шаблона → `waiting_top` → `waiting_bottom`. Можно вместо шаблона прислать своё фото (`waiting_photo`).
3. Текст чистится функцией `clean_text` (`meme_renderer.py:69`): убираются невидимые и управляющие символы, лишние пробелы. Пример: `"  привет​\x07   мир  "` превращается в `"привет мир"`.
4. Проверяется длина: больше 100 символов → «Слишком длинный текст: максимум 100 символов».
5. Pillow рисует текст (`build_meme`, `meme_renderer.py:294`). Это тяжёлая работа с пикселями, поэтому она идёт в отдельном потоке: `asyncio.to_thread(...)` (`handlers/meme.py:188`).
6. Готовый JPEG отправляется пользователю как превью. Telegram возвращает `file_id`, он сохраняется в таблице `memes`, а сама картинка на диске не хранится.
7. «Опубликовать» → `is_published = true`, мем появляется в ленте. Кнопки работают только под последним превью: бот запомнил id этого сообщения. Если нажать «Опубликовать» под старым превью (например, начав `/meme` заново), бот ответит «неактуален» и не опубликует новый мем вместо старого.

**Как подбирается размер текста** (`layout_text`, `meme_renderer.py:185`). Перебираются размеры шрифта от крупного к мелкому, и выбирается самый крупный, при котором текст помещается в 30% высоты картинки. Слова переносятся по ширине. Реальный результат для картинки 800×600:

| Текст | Шрифт | Строки |
|---|---|---|
| «когда открыл лабу» (17 символов) | 75 px | `КОГДА ОТКРЫЛ` / `ЛАБУ` |
| «когда преподаватель спросил про retry, а ты написала его сама и можешь объяснить каждую строчку» (95 символов) | 35 px | 4 строки |

Если текст не влезает даже мелким шрифтом, лишние строки обрезаются с многоточием: картинка не ломается. Фото тоже проверяется: только JPEG, PNG, WEBP, до 5 МБ и до 25 млн пикселей, поворот по EXIF, уменьшение до 1024 px по большей стороне.

**Если Imgflip не отвечает**, бот показывает запасные шаблоны (цветной градиентный фон) и сообщает об этом.

## 9. Сообщество и голосование

Лента (`/community`) показывает по одному мему с кнопками 👍 👎, стрелками и переключателем «🔥 Популярные / 🆕 Новые». Вся «память» ленты (сортировка, страница, id мема) лежит в `callback_data` кнопки.

**Голос** (`community_service.py:118`) проверяет по порядку:

1. значение только `+1` или `-1`;
2. мем существует и опубликован;
3. это не свой мем («За свой мем голосовать нельзя 🙂»);
4. вставка в `meme_votes`. У таблицы `UNIQUE(user_id, meme_id)`, поэтому второй голос того же человека БД отклонит («Ты уже голосовал за этот мем»);
5. счётчики меняются одним SQL-выражением.

Вот SQL, который SQLAlchemy реально генерирует для лайка мема №17:

```sql
UPDATE memes SET likes_count=(memes.likes_count + 1), dislikes_count=(memes.dislikes_count + 0),
                 rating=(memes.rating + 1) WHERE memes.id = 17
```

**Почему не «прочитать, прибавить, записать».** Представим, что Боря и Вика лайкают мем одновременно, а в нём 4 лайка:

| Время | Наивный способ в Python | Наш способ в SQL |
|---|---|---|
| t1 | Боря прочитал 4 | Боря: `likes = likes + 1` → 5 |
| t2 | Вика прочитала 4 | Вика: `likes = likes + 1` → 6 |
| t3 | Боря записал 5 | |
| t4 | Вика записала 5 (голос Бори потерян) | |

Так же защищён двойной тап по одному и тому же лайку: два апдейта пришли одновременно, первый вставил голос, второй получил ошибку UNIQUE и ответ «уже голосовал». Это проверялось на настоящем PostgreSQL.

**Бонус автору.** Когда рейтинг мема впервые достигает +5, автор получает +10 XP. Бонус выдаётся условным `UPDATE ... WHERE bonus_awarded = false`: даже при одновременных голосах он сработает только для одного из них.

## 10. Лидерборд

`LeaderboardService.get` (`app/services/leaderboard.py:44`) берёт 10 игроков с наибольшим XP. Если вы вне топа, место считается так: сколько игроков стоит выше, плюс один. Реальный SQL для игрока с id 5 и 240 XP:

```sql
SELECT count(*) AS count_1 FROM users
WHERE users.xp > 240 OR users.xp = 240 AND users.id < 5
```

При равном XP выше стоит тот, кто зарегистрировался раньше (меньший id). Таблица целиком не загружается, а индекс по `users.xp` делает запрос быстрым (на 20 000 игроков около 14 мс). Игроки с нулём XP в рейтинг не попадают: им бот пишет «Ты пока вне рейтинга: набери первый XP в викторине».

## 11. Внешние API, retry и graceful degradation

Все запросы наружу идут через один класс `ApiClient` (`app/core/http.py`). В нём:

- **timeout** 5 секунд на запрос;
- **retry**: до 3 попыток, пауза растёт вдвое (0,5 с, 1 с, …) плюс случайная добавка (`backoff_delay`, `http.py:50`);
- **классификация ошибок**: что повторять, а что нет.

Реальный лог, когда сервер дважды отвечает 503, а потом 200:

```
WARNING | app.core.http | giphy: попытка 1/3 не удалась (giphy: HTTP 503), повтор через 0.6 с
WARNING | app.core.http | giphy: попытка 2/3 не удалась (giphy: HTTP 503), повтор через 1.0 с
ответ: {'ok': True}
```

И когда сервис не поднялся за все попытки:

```
WARNING | app.core.http | giphy: попытка 1/3 не удалась (giphy: HTTP 503), повтор через 0.7 с
WARNING | app.core.http | giphy: попытка 2/3 не удалась (giphy: HTTP 503), повтор через 1.2 с
ERROR   | app.core.http | giphy: все 3 попытки не удались: giphy: HTTP 503
→ ApiUnavailableError
```

| Что случилось | Повторяем? | Ошибка в коде |
|---|---|---|
| таймаут, обрыв, HTTP 5xx | да | `ApiUnavailableError` |
| HTTP 429 (слишком часто) | да, с учётом `Retry-After` (не дольше 5 с) | `ApiRateLimitedError` |
| HTTP 401/403 (неверный ключ) | нет, повтор не поможет | `ApiAuthError` |
| другие 4xx (например, 404) | нет | `ApiClientError` |
| ответ не JSON или пустой | нет | `ApiBadResponseError` |

**Graceful degradation** означает: упал один сервис, работает всё остальное. Что видит пользователь:

| Сервис недоступен | Что происходит |
|---|---|
| Giphy | игра идёт как обычно; вместо GIF-реакции «GIF-сервис временно не отвечает. Продолжаем без него.»; для вопроса с картинкой Telegram пробует загрузить её по ссылке, а если не вышло, вопрос показывается без картинки |
| Imgflip | запасные шаблоны с цветным фоном и предупреждение |
| Reddit | «Мем дня» показывает запасной вариант и факт из викторины |
| PostgreSQL при старте | понятное сообщение «Сервер PostgreSQL не отвечает» и что сделать |

Где пользователь ждёт ответа прямо сейчас, попыток меньше: картинка вопроса скачивается за одну попытку, Giphy и Reddit используют две. Лучше показать вопрос без картинки, чем заставить ждать 15 секунд.

## 12. Кэш

`TTLCache` (`app/core/cache.py`) это словарь `ключ → (когда истекает, значение)`. Схема: сервис сначала смотрит в кэш, и только если там пусто или запись устарела, идёт в API.

Реальный пример (часы подменены, чтобы не ждать 6 часов):

```
t=0      get("imgflip:templates") → None        (пусто: идём в Imgflip, кладём на 6 часов)
t=1 ч    get("imgflip:templates") → ['Drake Hotline Bling', 'Distracted Boyfriend']   (API не вызывается)
t=6 ч+1с get("imgflip:templates") → None        (устарело: снова идём в Imgflip)
```

Что и на сколько кэшируется: шаблоны Imgflip 6 часов; картинки шаблонов и кадры Giphy 1 час; поиск Giphy 1 час (пустой результат 10 минут); посты Reddit 30 минут; токен Reddit на срок его жизни; «мем дня» до полуночи UTC; пометка «Reddit упал» 2 минуты, чтобы не долбить недоступный сервис.

Почему не Redis: бот работает в одном процессе, и отдельный сервер ради кэша только усложнил бы запуск. Интерфейс `get/set` такой же, как у Redis, поэтому заменить можно, поменяв один класс.

## 13. База данных, ORM и транзакции

**ORM** означает, что таблица описана классом, а запрос собирается из Python-выражений. Пример из кода:

```python
update(Meme).where(Meme.id == meme_id).values(rating=Meme.rating + value)
```

SQLAlchemy превращает это в SQL из раздела 9 и подставляет значения как параметры. Ручной склейки строк нет, поэтому нет SQL-инъекций.

**Что появляется в таблицах после одной игры Ани** (какие строки появляются, проверено на PostgreSQL; числа взяты из примера 1 раздела 6):

| Таблица | Что записано |
|---|---|
| `users` | строка Ани: `xp` вырос с 0 до 94, `level` с 1 до 2, `best_streak = 5` |
| `quiz_sessions` | одна игра: категория `nba`, `total_questions = 5`, `correct_count = 5`, `xp_earned = 94`, `finished_at` заполнено |
| `quiz_attempts` | 5 строк: какой вопрос, что выбрала, верно ли, сколько XP |
| `user_achievements` | 2 строки: First Win и «Без права на ошибку» |

**Связи** простыми словами: у пользователя много игр, в игре 5 ответов, у мема много голосов, а пользователи и достижения связаны «многие ко многим» через `user_achievements`.

**Транзакция на один апдейт.** Middleware открывает сессию, а в конце делает `commit` или `rollback` (`middlewares/db.py:34,37`). Пример пользы: если при ответе на вопрос что-то упало после вставки ответа, но до начисления XP, откатится всё, и не останется «ответа без XP».

Обратная сторона: ошибка в самом конце хендлера тоже откатила бы транзакцию. Поэтому «украшения», которые отправляются после основного экрана (GIF-реакция после игры, уведомление автору мема), обёрнуты в `try/except TelegramAPIError`: если Telegram их не принял, это пишется в лог, а XP и достижения сохраняются.

**SAVEPOINT.** Иногда нужно откатить не всю транзакцию, а только одну вставку. Например, второй голос за мем нарушил UNIQUE: `begin_nested()` (`community_service.py:130`) откатывает только эту вставку, а бот спокойно отвечает «уже голосовал».

**Миграции.** Схема создаётся не вручную, а командой `python -m alembic upgrade head` из файлов `alembic/versions/0001…0005`. Проверено: накат, полный откат и повторный накат проходят, а `alembic check` подтверждает, что модели совпадают со схемой.

## 14. async/await и потоки

Бот однопоточный, но асинхронный. Пример: Аня ждёт картинку из Giphy (сеть отвечает 2 секунды), а Боря в это время нажимает лайк.

- Без async бот стоял бы 2 секунды, и Боря ждал бы Аню.
- С async на строке `await client.request_json(...)` бот «отпускает» задачу Ани, обрабатывает лайк Бори и возвращается к Ане, когда Giphy ответит.

`await` ставится там, где ждём сеть или БД. Но рисование мема это работа процессора, а не ожидание, и `await` её не ускорит. Поэтому она вынесена в отдельный поток `asyncio.to_thread(build_meme, ...)`: пока Pillow рисует, бот отвечает остальным.

## 15. Dependency injection

Сервисы внешних API создаются один раз при запуске (`app/main.py`) и передаются в диспетчер:

```python
dp = Dispatcher(
    storage=MemoryStorage(),
    events_isolation=SimpleEventIsolation(),   # апдейты одного пользователя по очереди
    settings=app_settings, giphy=giphy, reddit=reddit, imgflip=imgflip,
)
```

Теперь любой хендлер получает нужный сервис, просто объявив параметр с таким именем:

```python
async def next_step(callback, callback_data, state, user, session, giphy: GiphyService): ...
```

`session` и `user` подставляют middleware, `giphy` берётся из диспетчера. Хендлер не создаёт объекты сам. В тестах вместо настоящего Giphy передаётся поддельный, и код хендлера при этом не меняется.

## 16. Что происходит при запуске

Реальный лог запуска (здесь без ключей Giphy и Reddit):

```
INFO | __main__ | Запуск МемоМастера...
INFO | app.database.seed | Вопросы викторины загружены: 43 шт.
INFO | __main__ | Giphy: выкл (нет ключа), Reddit: выкл (нет ключей)
INFO | __main__ | Бот запущен, ожидаю сообщения
INFO | aiogram.dispatcher | Start polling
```

По порядку `app/main.py`:

1. читает настройки из `.env`; если чего-то нет, объясняет, что исправить, и выходит;
2. проверяет подключение к PostgreSQL;
3. проверяет, что миграции применены;
4. загружает вопросы и достижения (повторный запуск безопасен);
5. создаёт HTTP-клиент, кэш и сервисы API;
6. готовит визуальные вопросы через Giphy (если есть ключ);
7. запускает long polling. `Ctrl+C` корректно закрывает соединения.

## 17. Безопасность на примерах

| Угроза | Пример | Защита |
|---|---|---|
| утечка токена в лог | в лог попала строка с `api_key=SECRETKEY123`, или трассировка ошибки скачивания файла содержит URL `.../file/bot<ТОКЕН>/...` | фильтр логов заменяет на `api_key=<hidden>`, токен бота на `<bot-token>`, причём и в тексте сообщения, и в трассировке (`app/core/logging.py:25`) |
| секреты в Git | | `.env` в `.gitignore`, в репозитории только `.env.example` без ключей; история проверена |
| HTML в имени | пользователь назвался `<b>Аня</b>` | имя экранируется, разметка сообщения не ломается |
| SQL-инъекция | | только ORM, значения передаются параметрами |
| накрутка голосов | двойной тап по 👍 | `UNIQUE(user_id, meme_id)` в БД |
| огромный текст или файл | 500 символов текста, фото 50 МБ | лимиты: 100 символов, 5 МБ, 25 млн пикселей |
| подделанная кнопка | `quiz:cat:hacker:0` | значения проверяются: бот отвечает «Неизвестная категория» (или «игра неактуальна», если кнопка пришла не на том шаге) |
| неподходящий контент | NSFW-пост в Reddit | фильтр `is_safe_meme`: без NSFW, спойлеров, видео, удалённых постов, только картинки с известных хостов |

## 18. Как устроены тесты

Запуск: `python -m pytest` (406 тестов, около 30 секунд, интернет не нужен).

Три подмены делают тесты быстрыми и независимыми:

- **БД:** SQLite в памяти вместо PostgreSQL;
- **Telegram:** `FakeTelegramSession` (`tests/conftest.py`) ничего не отправляет, а записывает, что бот пытался отправить;
- **API:** `FakeApiClient` возвращает заготовленный ответ или ошибку.

Пример сквозного теста: тест «нажимает кнопки» как человек и проверяет результат.

```python
await player.send("/start")
await player.press(MenuCB(action="play").pack())
await player.press(QuizCB(action="cat", value="nba").pack())
assert await player.state() == QuizStates.answering.state
```

Дополнительно 8 сценариев демонстрации прогонялись на **настоящем PostgreSQL** с тремя пользователями: 24 проверки из 24 прошли. Гонки (двойные нажатия, параллельные голоса) тоже проверялись на PostgreSQL.
